# API reference

## Base URLs and OpenAPI

Local Compose endpoints:

- HR Service: `http://localhost:8081`
- Leave Service: `http://localhost:8082`
- Through Web/Nginx: `/hr-api` and `/leave-api` on `http://localhost:3000`

Each service serves its OpenAPI document at `/openapi/v1.json` only in
Development. Example: `http://localhost:8081/openapi/v1.json`. The deployment
configuration defaults to Development for local use; do not expose development
OpenAPI endpoints unintentionally in production.

Unless stated otherwise, routes require `Authorization: Bearer <access-token>`.
Roles are `HR`, `Manager`, and `Employee`. HR owns organization/catalog
administration. Only HR and Manager can access approval inbox and decision
routes; the service additionally checks that a Manager is assigned to the
request. Refresh tokens are set as an HttpOnly cookie by HR login and are not
returned in JSON.

## HR Service

| Method and route | Access | Purpose |
|---|---|---|
| `POST /api/v1/auth/login` | Anonymous | Authenticate; returns access token and sets refresh cookie |
| `POST /api/v1/auth/refresh` | Refresh cookie | Rotate refresh token and return a new access token |
| `POST /api/v1/auth/logout` | Refresh cookie | Revoke refresh token and clear cookie |
| `GET /api/v1/me` | Any authenticated role | Current user's HR profile |
| `GET /api/v1/me/team` | Authenticated | Current manager's team |
| `PUT /api/v1/me/password` | Authenticated | Change own password |
| `GET /api/v1/departments[/{id}]` | Authenticated | Read departments |
| `POST /api/v1/departments` | HR | Create department |
| `PUT /api/v1/departments/{id}` | HR | Update department |
| `DELETE /api/v1/departments/{id}` | HR | Delete department when business constraints permit |
| `GET /api/v1/employees[/{id}]` | HR | List/read employees |
| `POST /api/v1/employees` | HR | Create employee; employee code is generated by the service |
| `PUT /api/v1/employees/{id}` | HR | Update employee |
| `POST /api/v1/employees/{id}/deactivate` | HR | Deactivate employee and revoke refresh tokens |
| `PUT /api/v1/employees/{id}/password` | HR | Reset employee password |
| `GET /api/v1/lookup/employees/{id}` | Authenticated service caller | Employee snapshot for Leave Service |
| `GET /api/v1/lookup/employees/{managerId}/team` | Authenticated service caller | Manager team lookup |
| `GET /api/v1/leave-types[/{id}]` | Authenticated | Read leave catalog |
| `POST /api/v1/leave-types` | HR | Restore a missing built-in type (ANNUAL, SICK or UNPAID); custom types are rejected |
| `PUT /api/v1/leave-types/{id}` | HR | Update leave type |
| `GET /api/v1/leave-policies[/{id}]` | Authenticated | Read policies; accepts `year` and/or `authoritative` query parameters |
| `POST /api/v1/leave-policies` | HR | Add a missing yearly policy for an active, balance-deducting built-in type; duplicate policies and UNPAID policies are rejected |
| `PUT /api/v1/leave-policies/{id}` | HR | Update policy |
| `GET /api/v1/holidays[/{id}]` | Authenticated | Read holidays |
| `POST /api/v1/holidays` | HR | Create holiday |
| `PUT /api/v1/holidays/{id}` | HR | Update holiday |
| `DELETE /api/v1/holidays/{id}` | HR | Delete holiday |

`GET /api/v1/leave-types` accepts `includeInactive` (HR only) and
`authoritative`. `authoritative=true` bypasses Redis and reads SQL.

## Leave Service

| Method and route | Access | Purpose |
|---|---|---|
| `GET /api/v1/leave-requests` | Authenticated | Requests visible to the caller's role |
| `GET /api/v1/leave-requests/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD` | Authenticated | Calendar requests, optionally date-bounded |
| `GET /api/v1/leave-requests/{id}` | Authenticated | Read request subject to visibility rules |
| `GET /api/v1/leave-requests/mine` | Authenticated | Current user's requests |
| `POST /api/v1/leave-requests` | Authenticated employee | Submit request |
| `GET /api/v1/leave-requests/pending-approval` | Manager, HR | Approval inbox |
| `POST /api/v1/leave-requests/{id}/approve` | Assigned Manager, HR | Approve request |
| `POST /api/v1/leave-requests/{id}/reject` | Assigned Manager, HR | Reject request |
| `POST /api/v1/leave-requests/{id}/cancel` | Authenticated owner | Cancel request when allowed |
| `GET /api/v1/leave-balances/mine?year=2026` | Authenticated | Current user's balance by leave type |

There is no standalone report/export endpoint. Dashboard metrics are derived
from the available employee, leave request, balance and calendar APIs. Export
and notification actions in the UI are not currently available.

## Request and response examples

### Login

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "employee@example.test",
  "password": "<configured-password>"
}
```

Response body:

```json
{
  "accessToken": "<JWT>",
  "expiresAtUtc": "2026-11-03T07:00:00Z",
  "fullName": "Demo Employee",
  "email": "employee@example.test",
  "userId": "00000000-0000-0000-0000-000000000001",
  "role": "Employee"
}
```

The response also sets the `hr_leave_refresh` HttpOnly cookie. Do not copy real
tokens into logs, tickets or documentation.

### Create a leave request

```http
POST /api/v1/leave-requests
Authorization: Bearer <JWT>
Content-Type: application/json
```

```json
{
  "leaveTypeId": 1,
  "startDate": "2026-11-09",
  "endDate": "2026-11-09",
  "reason": "Personal leave"
}
```

Successful creation returns `201 Created` with a `LeaveRequestResponse`:

```json
{
  "id": "00000000-0000-0000-0000-000000000002",
  "employeeId": "00000000-0000-0000-0000-000000000001",
  "approverId": "00000000-0000-0000-0000-000000000003",
  "departmentId": 1,
  "leaveTypeId": 1,
  "startDate": "2026-11-09",
  "endDate": "2026-11-09",
  "totalDays": 1.0,
  "reason": "Personal leave",
  "status": 0,
  "createdAtUtc": "2026-11-03T07:00:00Z",
  "balances": [
    {
      "leaveTypeId": 1,
      "year": 2026,
      "entitled": 12.0,
      "used": 0.0,
      "pending": 1.0,
      "available": 11.0
    }
  ]
}
```

`status` is the `LeaveRequestStatus` enum (`0` Pending, `1` Approved, `2`
Rejected, `3` Cancelled) in the default JSON serialization. Values and returned
balances depend on the database state and the user's policies.

Approval and rejection accept an optional note:

```json
{ "note": "Reviewed and confirmed" }
```

## Error contract

Application errors use `application/problem+json`. For example:

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 422,
  "detail": "Invalid request data",
  "errors": {
    "startDate": ["Start date must not be in the past."]
  }
}
```

| HTTP status | Meaning |
|---:|---|
| `400` | Malformed request or model-binding validation failure |
| `401` | Missing/expired/invalid access token or invalid credentials |
| `403` | Authenticated caller lacks the role or business authorization |
| `404` | Requested record does not exist or is not visible |
| `409` | Duplicate data, conflicting state or overlapping business operation |
| `422` | Business/input validation failure; response may include `errors` |
| `503` | Leave Service cannot access a required HR dependency |
| `500` | Unexpected server failure; response is sanitized, details are in server logs |

The exact `title` and `detail` depend on the endpoint and are not stable machine
identifiers. Clients should branch on the HTTP status and validation field keys.

The catalog is fixed to ANNUAL, SICK and UNPAID. HR create endpoints exist only
to restore one of those built-in types or add a missing policy for an active
type that deducts a balance; they do not enable arbitrary leave types or an
UNPAID entitlement policy. Existing policies can be updated by HR.
